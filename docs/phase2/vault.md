# E2.1 .env secret vault (true end-to-end encryption)

PRD: "Share API keys and passwords via client-side encrypted links that self-destruct after one view."
This is the one Zaagl feature where "zero-knowledge" is literally true: the server stores **only ciphertext and non-secret
metadata**. Encryption and decryption happen in the browser (or CLI) with a key that lives only in the URL fragment.

## Share URL
```
https://zaa.gl/<code>#k=<linkKey>&e=<encKey>
```
- `k` is the normal Phase 1 link key (ADR-0001): 128 bits minted by the server, stored only as SHA-256, sent by the viewer in
  `X-Zaagl-Link-Key`. It stops anyone who only knows (or guesses) the 30-bit code from burning the secret.
- `e` is the **encryption key**: 256 bits generated by the creating client. It is **never sent to the server**, in any
  header, body, query or log. The server cannot decrypt, cannot verify the key, and cannot recover the secret.
- The redirect `zaa.gl/<code>` answers `302 app.zaa.gl/v/<code>` (no fragment in `Location`); the browser keeps the
  fragment (RFC 9110 §10.2.2). The viewer reads `k` and `e`, removes the fragment with `history.replaceState`, and only `k`
  ever leaves the page.

## Client-side crypto contract (version 1) — the UI and CLI MUST implement exactly this
All primitives exist in WebCrypto (`crypto.subtle`) and in .NET (`AesGcm`, `HKDF`, `Rfc2898DeriveBytes.Pbkdf2`).

1. `encKey` = 32 bytes from `crypto.getRandomValues`, encoded base64url without padding (43 characters) as `e=`.
2. Optional passphrase (`passphraseProtected: true`): `salt` = 16 random bytes;
   `pk` = PBKDF2-HMAC-SHA256(passphrase as UTF-8 NFC, salt, **600,000** iterations, 32 bytes).
3. Content key: `cek` = HKDF-SHA256(ikm = `encKey` (‖ `pk` when a passphrase is used), salt = `salt` or 16 zero bytes,
   info = UTF-8 `"zaagl/vault/v1/cek"`, 32 bytes).
4. `iv` = 12 random bytes. Never reuse a `(cek, iv)` pair (a new `encKey` per secret makes this automatic).
5. `header` = `0x01` (version) ‖ `flags` (1 byte: bit 0 = passphrase) ‖ `salt` (16 bytes, present only when bit 0 is set).
6. `ct` = AES-256-GCM(key `cek`, iv, plaintext, **additional data = `header`**), 128-bit tag appended (WebCrypto default).
7. Envelope = `header` ‖ `iv` ‖ `ct`. Sent as base64url without padding in `ciphertext`.
8. Plaintext = UTF-8 JSON: `{"v":1,"type":"env"|"text","name":"<optional file name>","content":"<the secret>"}`. Clients
   SHOULD pad the JSON with a `"pad"` string of spaces to the next multiple of 1 KiB so the length does not reveal the size
   of the secret. Unknown fields MUST be ignored by readers.
9. Decryption reverses this; any GCM failure means "wrong key or passphrase" (the server cannot tell the difference and
   never sees a decryption attempt). A reveal that fails to decrypt has still consumed its view.

The server validates only the envelope **structure**, never its content: base64url, decoded size within the plan cap,
version byte `0x01`, known flags, and minimum length (`1 + 1 + [16] + 12 + 16`). The `passphraseProtected` field must match
flag bit 0. Future versions add a new version byte; the server accepts the versions listed in `VaultEnvelope.KnownVersions`.

## Data model (`devtools` schema, owned by DeveloperTools)
`devtools.secrets` (one row per resource, `resource_id` = `resources.resources.id`):
| column | type | notes |
|---|---|---|
| `resource_id` | uuid PK | |
| `owner_id` | uuid null | copy, for the owner list; null for guests |
| `ciphertext` | bytea null | the envelope; **null once wiped** |
| `ciphertext_bytes` | int | 30..1,048,576 |
| `envelope_version` | smallint | 1 |
| `passphrase_protected` | bool | non-secret flag so the viewer knows to ask |
| `max_views` | smallint | 1..100 |
| `views_used` | smallint | 0..max_views |
| `expires_at` | timestamptz | copy of the link's, kept current from C10 `LinkRenewed`; used by the wipe sweep only |
| `created_at`, `last_viewed_at` | timestamptz | |
| `wiped_at`, `wipe_reason` | timestamptz null, text null | `burned`, `deleted`, `expired`, `disabled`, `purged` |
Checks: `views_used <= max_views`; `(ciphertext IS NULL) = (wiped_at IS NOT NULL)`; size and version ranges.

`devtools.secret_events` (audit without contents): `id`, `resource_id`, `kind` (`created`, `revealed`, `burned`,
`deleted`, `expired`, `disabled`, `purged`), `views_used` after the event, `occurred_at`. **No IP, no user agent, no
ciphertext, no key.** Deleted with the secret at purge.

## Endpoints
Code: `src/Zaagl.Api/Endpoints/DeveloperToolsEndpoints.cs` (routes), `src/Modules/DeveloperTools/Application/VaultService.cs`
(rules), `VaultEnvelope.cs` (structure check), `DevToolsLifecycle.cs` (C10 wipe, purge handler, expiry sweep). Tests:
`tests/Zaagl.Api.Tests/Phase2/VaultApiTests.cs` (9 tests, including an independent implementation of the crypto contract).

| Method and route | Who | What |
|---|---|---|
| `POST /api/vault/secrets` | JWT, API key (`tools:write`) or guest (CAPTCHA `guest-vault`) | Create. Body `{ciphertext, passphraseProtected, maxViews?, expiresAt?, label?, password?, customSlug?}`. `201 {resourceId, code, shortUrl, linkKey, maxViews, expiresAt, isGuest}`. |
| `GET /api/vault/secrets` | owner (`resources:read`) | The owner's secrets, newest first (max 100): metadata only. |
| `GET /api/vault/secrets/{id}` | owner | Metadata, state, views used/remaining, audit events. Never the ciphertext. |
| `DELETE /api/vault/secrets/{id}` | owner (`tools:write`) | Burn now: link deleted (410) and ciphertext wiped in the same request. |
| `GET /api/public/vault/{code}` | link holder (gate: key, password grant) | Descriptor: `{state, maxViews, viewsRemaining, expiresAt, passphraseProtected, hasPassword, ciphertextBytes, envelopeVersion}`. **Consumes nothing**, so link-preview bots and page reloads are harmless. |
| `POST /api/public/vault/{code}/reveal` | link holder (gate) | Atomically consumes one view and returns `{ciphertext, viewsRemaining, burned}`. The last view wipes the ciphertext in the same transaction. |
Password unlock reuses `POST /api/public/content/{code}/unlock` (Phase 1); the grant goes in `X-Zaagl-Grant`.

Errors: `400 validation` (bad envelope, flag mismatch), `402 plan_required` (views > 1 on Free, password on Free),
`413 secret-too-large` (ciphertext over the plan cap), `404` (unknown code, wrong key),
`401 password-required`, `410 burned` (all views used or burned by the owner), `410 expired|deleted|disabled|taken-down`,
`429` (rate limits, guest counters).

## Race safety
`reveal` locks the row (`SELECT ... FOR UPDATE` inside a transaction, `lock_timeout 3s`), re-checks `ciphertext IS NOT
NULL AND views_used < max_views AND expires_at > now`, then increments and, on the last view, sets `ciphertext = NULL` in the
same statement. Under any concurrency exactly `max_views` reveals succeed; every other request gets `410 burned` (tested with
20 parallel reveals against `max_views = 1` and `= 3`). Same pattern as `DownloadGrants.ConsumeAsync`.

## Retention and wipe
- Burned (last view) or owner delete: ciphertext wiped immediately.
- Link expiry: the worker's vault sweep wipes the ciphertext of every secret whose `expires_at` passed (it does **not** wait
  for the 90-day quarantine: a secret is not kept "in case the owner renews"; renewing an expired secret is refused).
- Link disabled for abuse/safety, link deleted, link purged (C10 events): ciphertext wiped (handler is idempotent).
- Purge (`purge_after`, or expiry for guests): the rows themselves are deleted through `IResourceKindHandler`.
- Owner changes through `PATCH /api/resources/{id}`: `public` is refused for secrets (the link key is mandatory); renewal is
  allowed only while the secret is still available.

## Security and abuse analysis
- **Zero knowledge:** the server never receives `e`. The envelope is opaque; the server never parses plaintext and logs
  nothing of the body (Serilog request logging records method, path, status only). The owner API never returns ciphertext.
- **Guessing the code** gives nothing: the link key is required (404 otherwise, same timing class).
- **Preview bots and prefetchers** cannot burn a secret: only `POST .../reveal` consumes, and bots do not POST (addendum §8.2.4).
- **Lost view on decryption failure:** documented in the UI (show "wrong key or passphrase, the view was used").
- **Abuse (hosting encrypted payloads):** small caps (16-256 KB), short expiry, CAPTCHA and PD-14 counters for guests, normal
  takedown by code (`/api/reports`). The operator cannot inspect contents; takedown wipes the ciphertext.
- **Metadata leak:** only the ciphertext length (padding recommended), timestamps and view counts are visible to the server.
- **Owner label** (`label`) is plaintext metadata shown only to the owner, never in the public descriptor; the UI must say so.

## Plan gating (PROPOSED)
Guest, Free and Starter may create. Caps: ciphertext 16 KB / 64 KB / 256 KB; views 1 / 1 / up to 10; password Starter only;
expiry: content retention (7 / 7 / 30 days).

## What the UI needs
1. **Create** (`/vault/new` or a tray action): textarea or `.env` file drop, "views" selector (1..plan max), expiry picker,
   optional passphrase, optional password (Starter), optional alias; guests get the Turnstile widget (action `guest-vault`).
   The page encrypts locally, POSTs, then shows the full URL `shortUrl#k=linkKey&e=encKey` once with a copy button and a
   warning that Zaagl cannot recover it.
2. **Viewer `app.zaa.gl/v/<code>`** states: loading; `available` ("Reveal secret: this uses 1 of N views", passphrase field
   when `passphraseProtected`); password form on `401 password-required`; revealed (decrypted content, copy button, download
   as `.env`, "this secret is now destroyed" when `burned: true`); `burned` (410); expired/deleted/disabled/taken down (410);
   not found (404, also for a wrong key); decryption failed (wrong key or passphrase).
3. **Owner list and detail**: label, created, expires, views used / max, state (available, burned, expired, deleted), audit
   timeline, "Destroy now" button. Never a "show secret" button (the server cannot).
